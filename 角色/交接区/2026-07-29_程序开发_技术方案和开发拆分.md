## 3. 推荐技术方案

### 3.1 首版技术路线

推荐第一版原型使用 Python + Pygame 系列库实现，理由：

- 项目当前已经是 Python 项目，切换成本最低。
- MVP 是单机 2D 俯视角射击，不需要 Unity、Godot 或复杂 ECS。
- Pygame 足够覆盖窗口、输入、2D 渲染、音频、矩形/圆形碰撞和帧循环。
- 后续可用数据配置文件快速调敌人、道具、武器参数。

推荐依赖：

- 优先：`pygame-ce`，社区维护更活跃。
- 备选：`pygame`，若环境安装更方便也可接受。

注意：当前环境未安装 `pygame`。进入实现阶段前需要新增依赖声明并安装依赖。

### 3.2 建议运行方式

后续建议：

```bash
python main.py
```

`main.py` 只负责启动游戏，例如：

- 初始化配置。
- 创建 `Game`。
- 调用主循环。

实际逻辑放入 `src/` 或 `game/`，避免入口文件膨胀。

### 3.4 固定房间序列建议

建议首版明确采用固定房间序列：

```text
起始房 -> 战斗房1 -> 战斗房2 -> 奖励房 -> 战斗房3 -> 战斗房4 -> Boss房
```

原因：

- 显著降低地图生成、连通性、门逻辑、出生点合法性和寻路复杂度。
- 更利于调试房间状态机和战斗节奏。
- 可将每个房间的障碍物和出生点配置化，保留后续扩展到随机房间池的空间。

### 3.5 玩家控制方案

玩家移动：

- `WASD` 输入形成二维方向向量。
- 对角线移动需归一化，避免斜向速度更快。
- 每帧按 `velocity * dt` 更新位置。
- 玩家碰撞体建议先用圆形或较小矩形，和房间边界、障碍物做阻挡。

鼠标瞄准：

- 读取鼠标屏幕坐标。
- 若相机暂时固定，可直接用鼠标坐标减玩家坐标得到瞄准方向。
- 若后续加相机，需要从屏幕坐标转换到世界坐标。

射击：

- 鼠标左键触发。
- 武器使用冷却计时器控制射速。
- 基础手枪发射 1 发直线弹体。
- 散弹枪按扇形角度一次生成 3 到 5 发弹体。

冲刺：

- `Space` 触发。
- 使用冷却计时器和持续时间计时器。
- 冲刺方向优先使用当前移动方向；无移动输入时可使用当前瞄准方向。
- 冲刺速度用短时间高速度，而不是瞬移，便于碰撞处理。

是否加入短暂无敌帧：

- 建议加入，成本低且能显著减少冲刺过程中的挫败感。
- 实现方式：玩家增加 `invulnerable_timer`，冲刺开始时赋值，例如 0.12 到 0.20 秒。
- 受伤检测时若 `invulnerable_timer > 0` 则忽略伤害。
- 若实现阶段时间紧，仍可先保留字段和接口，把无敌时长配置为 0。

### 3.6 弹体、碰撞、伤害、生命、死亡方案

弹体：

- 用统一 `Projectile` 实体表示玩家弹和敌人弹。
- 字段包括：位置、速度、半径或矩形、伤害、阵营、存活时间、是否穿透。
- 每帧更新位置和寿命。
- 超出房间边界、撞墙、命中目标后销毁。

碰撞：

- 首版推荐使用简单几何碰撞：
  - 实体移动阻挡：矩形碰撞即可。
  - 弹体命中：圆形距离检测或 `pygame.Rect`。
  - 拾取道具：玩家圆/矩形与道具矩形重叠。
- 玩家、敌人、弹体、障碍物分组管理，避免全局混乱。

伤害：

- 用 `take_damage(amount, source)` 或类似方法统一处理。
- 玩家受伤需要触发受伤冷却或无敌帧，避免接触伤害每帧连扣。
- 敌人受伤后扣血，血量 <= 0 进入死亡流程。

生命：

- 玩家：`hp`、`max_hp`、`invulnerable_timer`。
- 敌人：`hp`、`contact_damage`、`death_reward`。
- Boss：同敌人，但血量更高，死亡触发胜利。

死亡流程：

- 敌人死亡：从活跃敌人列表移除，增加击杀数，按规则掉落。
- 玩家死亡：进入失败状态，停止房间推进和敌人行为，显示失败界面。
- Boss 死亡：进入胜利状态，显示胜利界面和基础统计。

### 3.7 房间状态机方案

推荐房间状态：

- `READY`：房间刚加载，门未关闭或等待玩家进入触发区。
- `ENTERING`：玩家进入房间，锁门并准备刷怪。
- `LOCKED`：门关闭，敌人生成。
- `COMBAT`：战斗中，持续检测敌人是否清空。
- `CLEARED`：敌人清空，生成奖励或通往下一房间的门。
- `EXIT_OPEN`：门打开，玩家可进入下一房间。
- `TRANSITION`：切换到下一房间。

最小流程：

1. 进入房间。
2. 如果是战斗房，关门并按配置刷怪。
3. 战斗中更新敌人、弹体、碰撞和 UI。
4. 敌人数量为 0 时清房。
5. 清房后生成奖励或打开出口。
6. 玩家进入出口触发下一房间。
7. Boss 房 Boss 死亡后进入胜利。

起始房和奖励房可复用同一状态机，但不刷怪。

### 3.8 敌人和 Boss 最小 AI 方案

近战敌：

- 状态：`idle`、`chase`、`attack/contact`、`hurt`、`dead`。
- 进入战斗后直接追玩家。
- 与玩家接触且伤害冷却结束时造成伤害。
- 不做复杂绕路，遇到障碍物可简单滑动或被阻挡。

远程敌：

- 状态：`idle`、`keep_distance`、`shoot`、`cooldown`、`dead`。
- 与玩家距离过近则后退，过远则靠近，中距离停留射击。
- 按固定间隔朝玩家发射慢速弹。
- 可不检查复杂视线；若障碍物挡住弹体，弹体自然撞墙销毁。

Boss：

- 状态：`intro`、`attack_projectiles`、`summon`、`cooldown`、`dead`。
- 攻击 1：朝玩家发射一组扇形或连续弹体。
- 攻击 2：短暂停顿后召唤 1 到 2 个近战敌，召唤物上限 2。
- 不做多阶段血量变化，最多根据血量降低冷却作为可选增强。

### 3.9 是否需要寻路

首版不建议做正式寻路。

替代方案：

- 房间采用固定矩形布局。
- 障碍物数量控制在 0 到 3 个。
- 敌人出生点避开封闭区域和障碍物背后。
- 近战敌使用直线追击加简单碰撞滑动。
- 远程敌主要站位射击，不依赖绕路。
- 如果发现敌人卡住，优先调整房间布局和出生点，而不是引入 A*。

仅当后续出现大量复杂障碍、分支房间、敌人频繁卡死时，再考虑网格寻路。

### 3.10 道具和敌人参数配置化

建议首版就做轻量配置化，但不要过度工程化。

推荐格式：JSON。

推荐配置文件：

- `assets/data/enemies.json`：敌人血量、速度、伤害、射击间隔、弹速、掉落权重。
- `assets/data/weapons.json`：武器伤害、射速、弹速、弹体数量、散布角度。
- `assets/data/pickups.json`：道具类型、数值、权重、显示名。
- `assets/data/rooms.json`：房间序列、房间类型、障碍物、门位置、敌人出生点、奖励规则。

配置加载建议：

- 启动时加载一次。
- 加载失败时给出明确错误。
- 代码中保留合理默认值，方便调试。
- 不需要热更新，不需要编辑器。

### 3.11 奖励方案

建议首版使用直接掉落，不做三选一界面。

理由：

- 直接掉落可以复用实体、碰撞和拾取系统。
- 三选一界面需要额外的 UI 状态、输入焦点、暂停战斗、选项生成和确认流程。
- 当前 MVP 的核心风险在战斗手感、碰撞和房间推进，奖励 UI 不是第一风险。

推荐最小规则：

- 每清理 2 个战斗房掉落 1 个强化道具。
- 低血量或固定房间可掉落小生命恢复。
- Boss 前确保至少 1 次强化。

三选一界面可作为第二轮增强。

## 4. MVP 开发任务拆分

### 4.1 项目基础

- 新增依赖声明：`requirements.txt` 或 `pyproject.toml`。

- `Menu/Victory/Defeat` 简单界面。

- 远程敌保持距离和间隔射击。

- 固定房间序列。

- 小生命恢复。
- 伤害提升。
- 射速提升。

### 4.8 Boss

- Boss 血量和受伤。
- 弹幕攻击。
- 召唤近战敌。
- Boss 死亡触发胜利。

### 4.9 UI 与反馈

- HUD：生命、武器、房间进度。
- 胜利界面：用时、击杀数、获得道具数。
- 失败界面：到达房间数、击杀数、生存时间。
- 基础音频事件接口，资源未完成前可先用占位音或静音降级。

### 4.10 测试与验证

- 配置文件能加载。
- 房间状态机按预期推进。
- 伤害和无敌帧不会重复扣血。
- 清房后门打开。
- Boss 死亡进入胜利，玩家死亡进入失败。
- 手动试玩验证 5 到 8 分钟流程是否完整。

## 5. 第一版原型开发顺序

推荐顺序：

1. 项目骨架和运行窗口：先让 `python main.py` 打开窗口并稳定退出。
2. 玩家移动、鼠标瞄准、基础渲染：确认操控手感最小闭环。
3. 手枪射击、弹体移动、边界销毁：确认射击闭环。
4. 碰撞和伤害：玩家弹打敌人、敌人死亡、玩家受伤。
5. 单房间战斗：一个房间内刷近战敌和远程敌，清空后开门。
6. 固定房间序列：从起始房推进到多个战斗房。
7. 道具直接掉落：清房后拾取强化，影响玩家数值。
8. 冲刺和短暂无敌帧：加入位移、冷却、受伤豁免。
9. Boss 房：Boss 两种攻击和胜利流程。
10. HUD、胜利/失败界面、基础音频触发。
11. 调参和完整跑通：确保一局能从开始推进到 Boss 或死亡。

关键原则：不要先做随机地图、复杂 UI、复杂动画、商店或永久成长。

## 6. 风险点和降低风险方案

### 6.1 依赖和环境风险

风险：当前没有依赖声明，且环境未安装 `pygame`。

降低方案：

- 实现前新增 `requirements.txt`。
- 明确推荐安装命令。
- 若 Python 3.13 下某个库兼容性有问题，优先切换到兼容版本或使用 `pygame-ce`。

### 6.2 项目结构过空

风险：当前没有任何游戏架构，直接在 `main.py` 堆代码会很快失控。

降低方案：

- 首轮实现前先建立最小模块边界。
- 保持结构轻量，不做复杂引擎化。

### 6.3 中文编码风险

风险：当前文档和工具输出存在乱码迹象，后续协作文档可能被破坏。

降低方案：

- 统一 UTF-8。
- 写入文件时显式指定 UTF-8。
- 主控汇总前检查生成文档是否可读。

### 6.4 房间状态机风险

风险：门、刷怪、清房、奖励、切房如果没有统一状态，容易出现重复刷怪、门状态错乱、胜负状态冲突。

降低方案：

- 先实现明确枚举状态。
- 每个状态只允许少量入口和出口。
- 为状态转换写最小测试或调试日志。

### 6.5 碰撞手感风险

风险：玩家卡墙、敌人卡障碍、弹体命中不准会直接影响可玩性。

降低方案：

- 首版障碍少而大。
- 玩家碰撞体小于视觉体。
- 敌人和弹体用简单碰撞形状。
- 先调房间布局，再考虑寻路。

### 6.6 AI 范围膨胀风险

风险：近战绕路、远程走位、Boss 阶段化会拖慢原型。

降低方案：

- 近战只直线追击。
- 远程只保持距离和射击。
- Boss 只做两种攻击轮换。

### 6.7 奖励 UI 范围膨胀风险

风险：三选一界面会引入额外 UI 状态和暂停逻辑。

降低方案：

- 首版直接掉落。
- 奖励配置保留权重，后续可接三选一。

### 6.8 调参风险

风险：敌人、武器、道具硬编码会导致后续调整成本高。

降低方案：

- 首版即使用 JSON 配置关键数值。
- 不做编辑器，只保证文件容易改。

## 9. 需要其他角色知道的信息

### 给游戏策划

- 固定房间序列非常适合作为首版实现方案，程序侧建议批准。
- 三选一奖励界面建议后延，首版用直接掉落即可验证成长反馈。
- 冲刺短暂无敌帧实现成本低，建议进入首版，但时长应配置化。
- 不建议首版做寻路；请在房间设计上避免复杂迷宫和封闭障碍。

### 给美术设计

- 首版需要清晰区分：玩家、近战敌、远程敌、Boss、玩家弹、敌人弹、生命道具、强化道具、门、障碍物、地面。
- 建议资源先按俯视角 2D 制作，碰撞体以简单圆形或矩形为准。
- 玩家和普通敌人可以先用少帧或静态图，Boss 可用放大体型加颜色/轮廓区分。
- 障碍物建议少量、大块、边界清晰，避免复杂凹形碰撞。

### 给音效音乐

- 程序侧建议以事件名接入音效：`player_shoot`、`enemy_hit`、`player_hit`、`enemy_die`、`pickup`、`door_open`、`dash`、`victory`、`defeat`、`boss_attack`。
- 首版音效资源可以先占位，关键是触发时机稳定。
- 背景音乐可先 1 条通用战斗循环，Boss 音乐可后续增强。

### 给主控窗口

- 当前项目还不是游戏项目，只是 Python 示例工程加协作文档。
- 进入功能开发前应先确认依赖选择：`pygame-ce` 还是 `pygame`。
- 建议尽快处理中文编码显示/写入问题，否则后续交接文件和汇总可能继续乱码。
